Slide 1

Nikipokeとは何か

ブラウザで遊べるポケモン対戦体験を、仕様準拠のバトルエンジンから組み立てようとしているリポジトリ。

  • Rust製バトルエンジンと TypeScript 製 UI を分離
  • AI対戦とリアルタイム対戦の両立を視野に入れる
  • 単なる試作ではなく、仕様・実装・体験を同時に育てている
EngineRust core loop
FrontendReact + Vite
GoalPlayable battle demo

Speaker Notes

話すポイント

Nikipoke は、ポケモン対戦のロジックを Rust で持ちつつ、ブラウザから遊べる体験につなげようとしているプロジェクトです。単なる UI モックではなく、将来的には AI 対戦やプレイヤー同士の通信対戦まで見据えた構成になっているのが特徴です。

Slide 2

リポジトリの全体像

  • `engine-rust` が対戦状態遷移のコアを担当
  • `frontend` が React + Vite の画面基盤を担当
  • 仕様書と監査レポートが同居し、実装との差分を確認できる

Speaker Notes

構成の見方

リポジトリは大きく三層に分かれています。中核は engine-rust で、対戦の進行やダメージ計算などを扱います。frontend は React と Vite を使った UI 側で、さらに仕様書や監査レポートがあるため、何を実装したいかと今どこまでできているかを同じ場所で追える構成です。

Slide 3

バトルエンジンの強み

  • 最小かつ決定的なコアループを Rust で再実装
  • step_battle と replay_battle で検証しやすい
  • Minimax と MCTS を使う AI の土台も用意済み

Speaker Notes

技術的な強み

エンジン側の強みは、対戦を 1 ターンずつ進める明確な API を持っていることです。状態を作り、行動を与え、結果を返すという形が揃っているので、UI 接続にも AI シミュレーションにも使いやすいです。リプレイや探索系の関数があるため、将来の検証自動化や AI 強化にもつながります。

Slide 4

仕様書が示す再現対象

  • 第9世代基準で能力値、ダメージ、ターン処理を整理
  • 急所、タイプ相性、状態異常、優先度まで含めて定義
  • 実装より先にゴールの輪郭がかなり明確になっている

Speaker Notes

仕様の価値

Pokemon Battle Spec.md はかなり厚い資料で、対戦システムの主要ルールを体系立てて整理しています。能力値計算やダメージ式だけでなく、ターン終了時の処理順や状態異常の細かい仕様まで書かれているので、実装のゴールが曖昧になりにくいのが大きな価値です。

Slide 5

現時点の到達点

  • 監査時点で cargo test は 50 件成功
  • 状態遷移フレーム、行動順、基本ダメージ処理は成立
  • WASM ビルド経由でブラウザへ接続できる見通しがある

Speaker Notes

ここまで進んでいること

監査レポートでは、基盤そのものは成立していると評価されています。まだ完全再現ではないものの、対戦の流れを前に進めるフレームはできており、テストも通っています。さらに WASM パッケージとしてフロントエンドから利用する導線も README に示されているので、体験に落とし込む筋道はあります。

Slide 6

いま大きいギャップ

  • manual 技の多くが実質 no-op
  • ダメージ補正順、やけど、壁、天候の再現が不足
  • 状態異常、勝敗判定、ダブルバトル仕様に差分が大きい

Speaker Notes

課題の重心

一方で、公式仕様への準拠度はまだ低いと監査で指摘されています。特に manual 扱いの技が十分につながっていないこと、ダメージ補正や状態異常の細部が未実装であること、勝敗判定やダブルバトルまで含めるとモデル自体の拡張が必要なことが、現時点の大きな課題です。

Slide 7

プロダクトとしての構想

  • フロントは React 19 + Vite + Tailwind CSS 4
  • タイトル、ロビー、バトル、リザルトまで画面構想がある
  • PvAI、PvP、観戦モードまで段階的に広げる計画

Speaker Notes

体験設計の面白さ

frontend_draft.md では、UI と体験の全体像がすでに整理されています。ログインからホーム、デッキ作成、対戦、結果画面までの流れがあり、まずローカル対戦、その後 PvP、さらに AI 戦や観戦へ進めるロードマップもあります。エンジンをただ実装するだけでなく、遊べるプロダクトにする視点が入っているのが良い点です。

Slide 8

次に進める優先順位

  • まずは P0 ギャップをテスト付きで潰す
  • step_battle の差分検証で正しさ確認を自動化する
  • その上で UI 接続と対戦デモを最速で成立させる

Speaker Notes

次の一手

次の一手としては、仕様との差分が大きい箇所をテスト込みで詰めることが重要です。監査レポートが提案している differential testing は特に有効で、自前エンジンと参照実装の差を機械的に検出できます。これで土台の信頼性を上げたうえで、フロントエンドとつないだ動くデモを早く出すのが、チームの勢いも作りやすい進め方です。

Slide 9

まとめ

  • 「遊べる対戦体験」と「仕様準拠エンジン」の両立を狙っている
  • コア実装は前進しているが、公式再現には重点課題が残る
  • 仕様・監査・UI 構想が揃っており、次の判断がしやすい

Speaker Notes

締め

このリポジトリの良さは、コードだけでなく、仕様書、監査、画面構想まで揃っていることです。だからこそ、どこが強みでどこが未完成かを共有しやすい状態になっています。今後は仕様差分の解消と、デモとして触れる体験づくりを並行して進めることで、価値が一気に見えやすくなるはずです。
